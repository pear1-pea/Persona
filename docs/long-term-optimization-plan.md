# Persona 长期优化方案

更新日期：2026-10-28。规划窗口：未来约六个月，按验收结果滚动调整。

Persona 已具有端云聊天、模型管理和账号体系，但当前实现尚未完成统一的构建、集成与真机验收，部分生命周期、数据所有权和请求终止边界仍有缺口。后续需要把这些能力可靠地交付给用户，并尽早验证人格与记忆带来的实际价值。

本方案沿现有 Kotlin、Room、MNN 与 Node/TypeScript 架构演进。优先交付可靠会话、Persona 产品闭环和可治理记忆，再依据质量及设备数据选择运行时优化和新技术实验。

## 1. 目标与成功标准

长期目标：构建以 Persona 为核心、使用用户授权记忆、支持受控端云协同，并能通过评测持续改善体验的 Android 应用。

主要用户流程：创建或发现 Persona → 开始聊天 → 根据隐私与设备能力执行 → 保存和恢复会话 → 管理明确授权的记忆 → 在后续会话正确使用。

成功需要同时满足：

- 可靠：模型可安装、加载、停止、切换和删除，错误后可恢复。
- 可控：账号、Persona、会话和记忆的边界清晰，禁止出端的数据不会在 fallback 或渲染中外传。
- 有用：角色表达稳定，记忆提高相关对话质量，用户能够纠正和删除信息。
- 可验证：改动具有固定基线、回归用例和可重复的 Windows/CI 验证结果。

## 3. Mac、Windows 与 CI 协作方式

| 环境 | 主要职责 | 不能替代的验证 |
| --- | --- | --- |
| Mac | 探查、实现、Review、文档；可运行的 Backend/packager 检查 | Windows Android 构建与设备行为 |
| Windows | Android 编译、JVM 测试、安装、arm64 真机及性能验收 | CI 的干净 checkout 验证 |
| CI | 固定依赖环境的构建、单元测试、packager 和隔离数据库 smoke | 真实设备推理、热状态及持续性能 |

Mac 不安装 Android 环境是既定分工，不是项目缺陷。Android 结果以 Windows 或 CI 的实际日志为准；MNN 真机结果由 Windows 连接设备验证。

每轮交接包含：版本/完整补丁清单、待验证行为、命令、预期结果。必须覆盖新增和未跟踪源码，尤其是 `.github/`、`tools/`、测试及新辅助类。`local.properties`、`.env`、模型文件和凭证在各环境独立配置，不进入源码交接。

Windows 基础命令：

```powershell
.\gradlew.bat assembleDebug --stacktrace
.\gradlew.bat testDebugUnitTest --stacktrace
.\gradlew.bat lintDebug
```

lint 先建立历史问题基线，再逐步设阻断规则。工具链与 Backend 命令沿用 [build.md](agent/build.md) 和 [baseline.md](qa/baseline.md)。真机测试使用 arm64 设备；当前仅打包 arm64 ABI，普通 x86_64 模拟器不能替代本地推理验收。

验收记录绑定版本、日期、命令、完整日志及退出码；设备测试增加型号、系统、模型包哈希、运行配置、输入样例和冷/热状态。缺少条件记为 Pending，执行失败记为 Failed。

## 4. 产品范围与架构演进

近期产品主线为 Persona 创建/编辑、公开与私有角色、发现/搜索、持续聊天、模型管理和记忆管理。Feed 的模拟内容应明确标识或调整展示，刷新与错误恢复要形成闭环。

真实 Post、点赞、评论和关注作为独立产品决策。只有确认社交互动是核心需求，并能承担服务端权限、内容生命周期和运营成本时，才开启完整社交主线。

保留现有层次，先明确责任，再按可测试边界提取模块：

| 职责 | 演进方向 |
| --- | --- |
| 对话编排 | 先由现有链路承担；复杂度需要时提取单一协调者 |
| 模型生命周期 | 选择、加载、停用、切换、删除共享操作所有者 |
| 路由与权限 | 先确定允许路径和可用性，再做质量、延迟与成本选择 |
| 上下文规划 | 分配应用规则、人格、历史、记忆和输出预算 |
| 执行 | 继续使用 MNN 与 CloudChatRepository；有真实扩展需求再统一执行器接口 |
| 记忆 | 独立管理写入、来源、检索、权限、修订与删除 |
| 观测与评测 | 覆盖整条链路，输出结果用于下一轮决策 |

`HybridAiRepository` 是演进起点。近期不要求将它扩展成所有职责的统一容器，也不为了架构图提前创建空接口。

## 5. P0：验收当前工程基线

目标是得到完整、能构建、能测试的候选版本，并建立真实问题清单。已有工具、测试和 CI 作为验收对象，不重复从头建设。

首先处理 [ModelPackageInstaller](../app/src/main/java/com/example/persona/core/ai/ModelPackageInstaller.kt) 中 `Failure` data class 的非属性构造参数；这是静态语言规则层面的编译阻断，修复后由 Windows 编译确认。随后按构建输出继续定位，不把当前已发现项视为全部错误。

P0 交付：

- 复核并汇总当前已跟踪、未跟踪改动，形成双方一致的候选版本。
- Windows 执行 Debug 构建和 JVM 测试，保存完整输出。
- 验收现有 CI；从干净 checkout 检查依赖、新增文件和 MNN 来源是否齐全。
- 复核 Backend、packager 已通过检查；改动影响相应范围时再运行。
- 在隔离数据库运行 auth/persona smoke，明确它未覆盖真实云端聊天。
- 准备固定真实模型包和一台可重复测试的 arm64 设备。

新增测试优先覆盖真实行为缺口：两次失败后的恢复、并发模型操作、跨账号清理、取消与断流、预算准入和两端模型包契约。JVM fake 可验证协调逻辑，不能证明 JNI、SAF、系统调用或真实推理正确。

UTF-8 累积、停止词等纯 C++ 逻辑可提取后在 Mac 做宿主机测试；MNN API、状态和 KV 行为仍由 Windows 连接真机的集成验证确认。

验收门：候选版本在 Windows 与 CI 可重复构建，适用单元测试通过；剩余集成与设备项有明确状态。当前阶段不承诺已经具备稳定的发布版本。

### 6.1 模型交付与操作所有权

保留 SAF 导入 → staging → 完整校验 → 原子安装的路线，先验证已有实现。

- Python 打包工具与 Android validator 共享正反样例；缺失/错误的 `llm_model`、路径、大小、哈希和必需文件必须获得一致结论。
- 现有删除顺序已调整，继续消除非当前模型被并发选中、重复删除及全局 boolean 被提前清除的窗口。
- 激活、切换、停用和删除经过同一协调边界；保护覆盖检查、资源释放、文件操作和状态发布。
- 文件删除失败时保留可解释状态；安装或进程中断后能识别、清理或恢复 staging。
- 分别校验已安装模型的运行资源与安装所需临时空间，不以单一固定剩余空间阈值替代容量规划。

验证缓存建立在不可变版本目录、安装记录和文件清单上。完整哈希保留在安装和必要的重新验证阶段；日常扫描可采用轻量检查。`size + mtime` 仅用于失效提示，不能被描述为可信完整性证明。

官方分发包增加可信发布清单或签名、公钥来源、版本及撤销策略。用户自行生成的包明确显示来源未验证。签名解决发布来源，仍需文件完整性与兼容性校验。

### 6.2 失败恢复、可用性与隐私

失败分类和退避已有，重点统一初始化、准入和 Router 的判断来源。当前失败次数除以常量的“失败率”应调整；两次失败后直接上云不能永久绕过退避后的探测。

重试策略区分永久损坏、兼容性错误、临时内存/资源压力、用户取消和未知失败。允许恢复时提供明确的重试入口，包括当前已选模型；用户取消不触发云端重启。成功探测与完整生成的健康证据分别记录，避免短 smoke 成功无条件掩盖持续生成失败。

永久失败与临时失败计数采用不同的失效规则；不能因为统计窗口过去就自动解除损坏或不兼容状态。重新验证、重装或明确重试才更新该状态。

路由先计算允许执行器与硬性资源限制，再判断当前可用性，最后选择本地、云端或受限级联。禁止出端且本地不可用时返回明确不可执行结果；`forceCloud` 不能隐式覆盖禁止出端的授权。

Fallback 是新的执行决策，重新检查权限、账号和上下文；`latencyBudgetMs` 在有真实调用方与策略意义时接通，否则删除未使用的承诺。

### 6.3 账号、会话与本地数据

当前消息已有 owner 过滤，仍需修复全局 Persona 父记录级联删除跨 owner 消息的风险。角色资料快照、用户会话和私有记忆分别定义所有权及保留规则，迁移前备份可恢复的测试数据并验证删除边界。

生成开始时固定账号、会话及请求身份。账号变化后，旧生成、迟到回调和数据库检查点不能写入新身份；旧请求 401 只使其对应 session 失效。

退出登录、注销账号、清理聊天、删除 Persona 和删除记忆采用明确而不同的策略。注销中的本地清理由可恢复的协调逻辑承担，不依赖短生命周期 UI coroutine 完成全部步骤。`OFFLINE_USER` 数据独立管理，不自动归入登录账号。

账号隔离正确后，再根据目标分发方式与威胁模型评估数据库加密、密钥生命周期和用户导出。已有备份排除规则继续验证；加密不能替代查询、外键和缓存隔离。

### 6.4 云端代理与网络终止

- 修复只等待 `drain` 的背压路径，使关闭、错误和取消均能结束等待，所有路径释放并发槽。
- 明确预算预留、执行、失败释放和结算语义。并发拒绝不错误扣减；不能因错误退款允许绕过实际已发生的服务端成本。
- 输入/输出预算更新具有一致的准入边界，结算具备请求身份与重复调用保护。
- 当前进程内并发计数明确限制单实例部署；多实例上线前实现共享协调及故障释放。
- 区分连接、首响应、流空闲和总体预算；已有服务端整体超时不替代客户端保护。心跳不等于有效生成进度。
- 登录/注册客户端也具备明确的 HTTPS、目标服务、重定向和超时策略。
- 集成测试使用可控上游覆盖慢首包、持续流、半途断流、取消、429、异常格式与背压；真实 DeepSeek 验收另行记录。

### 6.5 生成参数与上下文契约

本地先验证 MNN 3.6.1 的配置生效时机：当前 JNI 在 load 后更改配置，而采样器在 load 时构造，需通过 Native 行为或有效采样器状态确认。云端修复合法参数被服务端硬编码覆盖的问题。

应用层提供少量任务预设，记录请求配置、有效配置和版本。能力不支持的参数显式拒绝或报告；云端仍由服务端限制模型、输出和资源，不要求各执行器支持完全相同的参数。

统一本地与云端的预算原则：不可裁剪应用规则、Persona 资料、历史、记忆、当前输入和输出分别分配预算。保留完整对话轮次优先；无法容纳硬约束或当前输入时明确提示，避免静默裁掉重要规则。云端同时满足服务端消息数、单条字符数及整体预算。

公开 Persona 资料属于不可信输入。使用结构化边界、模板控制标记处理与恶意样例回归；提示词不能作为数据权限执行机制。生成的 Markdown 图片与链接也受出站策略约束，尤其是本地和私人记忆场景。

P1 验收门：固定模型包可完整安装、加载、生成、取消、再次生成、切换和删除；并发及异常用例不越权、不跨账号删数据、不产生重复终态；禁止出端路径可验证。按 [真机计划](qa/native-test-plan.md) 与 [交付验收](qa/model-package-acceptance.md) 保存 Windows 实测记录。

## 7. 性能基线与 Runtime 优化方法

最小测量从 P1 开始，优化按瓶颈排序，不要求完成全部性能实验后才进入产品阶段。

| 指标 | 必须明确的口径 |
| --- | --- |
| 用户感知首屏延迟 | 点击发送至第一段文本显示，包含排队、加载和规划 |
| 模型加载 | 冷启动与复用加载分开，记录文件/运行配置 |
| Prefill / Decode | 使用运行时阶段指标，分别报告输入处理和生成速度 |
| 输出 Token | 实际生成、重新分词和字符估算分别标记 |
| 内存 | RSS/PSS 及采样方法、峰值窗口，不能相互混称 |
| 取消延迟 | 用户操作至执行停止、终态持久化及下一次可用 |
| 持续性能 | 相同负载持续运行，记录温度、系统热状态和吞吐变化 |
| 产品性能 | 气泡更新、Markdown 耗时、掉帧及 Room 写入次数 |

现有首 Chunk 计时不含此前上下文规划，输出数除以总耗时也不是纯 Decode 速度。先修正标签与观测边界，再比较优化。

当前已验证真机固定 CPU、Qwen2.5-0.5B、模型包和输入；记录冷/热、短/长输入及取消场景，报告样本数和分布，并在同一设备上用 1.5B 测试资源压力。其他内存档位的适配按实际需求扩展，4GB 真机测试不阻塞当前 P1。模型标称 context window 与设备有效窗口分离，后者由实测限定。

实验顺序：确认有效配置 → 识别热点 → 只改变主要变量 → 复跑相同负载 → 比较质量、延迟、内存与取消 → 采用或停止。Java memory class 不作为 Native 可用内存硬上限，OOM/进程被杀也不能承诺由 Kotlin 异常完整捕获。

`generate(1)` 循环位于 C++，分别测步进和 Native→Kotlin 输出回调开销。批式生成仍需逐一验证 UTF-8、停止词、EOS、最大输出、取消与 KV 一致性；停止响应和正确性退化时不接受该优化。

默认 Raw ChatML 路径每轮 reset，不能仅凭存在 `syncPromptCache` 就认定缓存生效。先检查实际路径、配置、命中率及正确性，再评估磁盘前缀复用；同时区分 Prompt/KV 缓存与编译缓存。私人缓存按账号/Persona 隔离，并在删除和配置变化后失效。

## 8. P2：Persona 产品闭环与显式记忆

### 8.1 核心产品和聊天体验

创建/编辑 Persona 后，相关列表可靠刷新；Profile 统计与分类来自真实数据。生成 JSON 完成解析后，再做必填字段、空值、长度、数组数量等业务校验；最多一次受控修复，仍失败则提示用户，不保存半成品。

流式优化优先拆开显示与持久化：内存生成态提供及时文本，Room 提供恢复检查点，完成/失败/取消立即提交终态。周期写入不能覆盖新终态；后台与进程重启恢复按明确策略测试，检查点间隔根据允许的数据损失窗口决定。

重复检测维护增量或有界窗口，避免每次 Delta 全文复制、归一化和切句。生成中采用轻量显示，完成后完整 Markdown；长代码块、表格、长列表和特殊字符进入性能回归集。优化收益由 Windows 真机测量确认。

### 8.2 第一版记忆闭环

在 P1 的身份、删除、隐私和上下文边界通过后，实现“用户明确要求记住/手工保存 → 查看与编辑 → 跨会话使用 → 删除后不再召回”。首版不依赖自动提取、Embedding 或复杂向量索引。

记忆支持用户偏好、稳定事实、阶段目标和 Persona 关系信息；区分账号级与 Persona 私有范围，共享必须有明确授权。用户事实、角色虚构、助手推断、模拟 Feed 和失败输出不能混为一种来源。

逻辑字段至少表达：owner、作用域、类型、内容、来源引用、事实/推断属性、确认状态、创建/修订与有效时间、出端授权、状态及版本。字段按产品需求落为表和关系，不把所有能力塞入一个 JSON。

来源可能包含多条消息。用户确认优先于模型自报置信度；用户编辑产生新版本并使派生索引失效。删除需要阻止摘要、缓存或排队提取任务再次写回同一信息，同时诚实说明历史回复不会被追溯改写。

权限在候选检索前过滤，注入前复核；fallback 到另一执行器时重建允许使用的记忆上下文。

### 8.3 人格与记忆评测提前启动

从 P0/P1 即可并行准备小型固定中文用例；首轮建议 30～50 条覆盖主要风险的案例，随着错误类型扩充，而非追求测试数量。

- 人格：语言、风格、角色设定、多轮一致性、重复和设定冲突。
- 记忆：显式召回、相关性、事实更新、时间、未知信息与删除后不再使用。
- 边界：账号/Persona 隔离、禁止出端、取消、恶意资料与模板标记。

开发集与保留集分开；模型、Prompt、参数和检索策略分别版本化。主观质量做成对比较与人工抽查；自动裁判不能单独决定发布或隐私行为。

P2 验收门：用户可完成创建/发现/聊天/恢复流程；显式记忆可跨会话使用、追溯、纠正和删除；固定评测集能检出角色与边界回归。数据来自测试与自愿反馈，不默认上传真实聊天。

## 9. P3：受控自动记忆与混合检索

显式记忆已证明有用后，再逐步引入以下能力，每步与前一基线比较。

| 子阶段 | 交付 | 主要验证 |
| --- | --- | --- |
| 候选提取 | 从允许的来源提取候选，去重、冲突检查，必要时确认 | 错写、虚构来源、跨账号和异步重复写入 |
| 摘要 | 有界压缩较早对话，保留来源与版本 | 关键事实遗漏、过期事实和错误传播 |
| 中文关键词检索 | 结构化条件加经过评测的分词/全文索引 | 两字词、人名、别名、中英混合与否定 |
| 可选语义检索 | 小型 Embedding、候选合并与简单排序 | 召回收益、内存、延迟、索引重建和删除 |

自动写入经过价值、权限、来源、重复与冲突判断；提取任务具有稳定身份，账号切换或来源删除后不继续落库。第一版不强求复杂重排序模型。

项目使用 Room 2.6.1；FTS5 不是直接可用的注解替换。先比较现有 FTS4、预分词和简单查询；需要 FTS5 时单独评估 Room/SQLite driver 迁移。默认 unicode61 不等于中文分词，trigram 全文查询又存在短查询限制，必须用实际中文用例验证。[Room 官方说明](https://developer.android.com/jetpack/androidx/releases/room3)、[SQLite tokenizers](https://www.sqlite.org/fts5.html#tokenizers)。

Embedding 选型考虑中文召回、量化误差、冷启动、与聊天模型同时驻留的峰值资源和可用导出路径。小数据先比较简单向量扫描；只有查询规模和性能证据需要时才引入 ANN/HNSW 或独立数据库。

分别测检索证据召回与生成答案正确性，避免把检索问题和小模型使用证据的能力混为一谈。评测涵盖知识更新、时间推理和无证据拒答，可参考 [LongMemEval](https://github.com/xiaowu0162/longmemeval)。

P3 验收门：相比显式/结构化记忆基线，目标任务质量有可重复改善，资源与延迟在设备预算内；权限、冲突、修订和删除用例通过。若没有收益，保留更简单方案。

## 10. P4：依据收益开展技术实验

P4 是条件式实验池，不是必须全部实现的交付清单。基础门槛通过后可提前做小型验证，但每次只保留一个明确范围的技术实验。

| 方向 | 启动条件 | 停止或回退条件 |
| --- | --- | --- |
| 新模型 | 当前质量边界明确，有许可与可用 MNN 导出路径 | 中文/人格收益不足，资源或取消退化 |
| OpenCL/GPU 等后端 | CPU 基线已证明存在相应瓶颈，有目标设备 | 驱动兼容、持续性能或内存抵消收益 |
| 磁盘 Prefix Cache | 内存复用正确且前缀处理成本显著 | 命中低、失效复杂或私人数据隔离不足 |
| 质量级联 | 某类任务有可信验证器，用户允许升级 | 总延迟/成本增加而任务成功率无改善 |
| 系统模型 | 目标设备支持，任务、语言和生命周期符合能力 | 可用覆盖不足或无法满足后台/隐私策略 |
| LoRA | 稳定风格缺陷被评测证实，已有高质量授权样本 | 保留集收益不足或部署后资源/能力退化 |
| 受控工具工作流 | 有明确真实任务和可验证应用接口 | 权限、取消、幂等或恢复不能保证 |
| 投机解码/MTP 等 | Decode 瓶颈明确，运行时与模型实际支持 | 附加内存、接受率和复杂度抵消收益 |

模型参数量仅作筛选线索，不能直接推导手机峰值内存或速度。每个候选完整验证 tokenizer、模板、输出格式、算子、运行时和设备性能；当前 Qwen2.5 保持为对照。LoRA 没有统一“1,000 条即可启动”的门槛，样本目标与保留集改善优先。

系统模型是可选能力。ML Kit Prompt API 的 API 26+、设备支持、前台与配额约束，应与 Persona minSdk 24 分开处理；不为了一个可选执行器默认提升全产品最低系统版本。[Prompt API](https://developers.google.com/ml-kit/genai/prompt/android/get-started)、[运行约束](https://developers.google.com/ml-kit/genai)。

路由按“规则 → 统计评估 → 有需要时轻量预测”演进。JSON 用 schema、工具调用用参数/权限/执行结果、记忆回答用证据验证；普通聊天先用回归集与人工反馈。模型自评分数不能当作可靠升级依据，在线探索不得突破用户硬约束。

受控 Agent 先做可暂停、可恢复的单一工作流。模型提出候选动作，应用验证并执行；发布、发送和账号安全变更依风险要求确认，不以“模型已生成参数”作为执行成功的证据。

## 11. 发布、可观测性与数据治理

发布准备从 P1 开始逐项建设，公开分发前完成：正式标识与版本、签名材料隔离、Release 构建、安装升级与数据迁移、依赖/模型许可及兼容性记录。R8 在 JNI、反射和序列化的 Release 回归通过后启用；已有 16 KB 链接配置仍需验证最终二进制与设备行为。

MNN 的 submodule revision 或下载制品摘要与构建结果绑定，本地源码覆盖也记录实际 revision。共享内核行为的依赖更新按小步进行，避免同时更换模型、运行时、Prompt 和采样策略。

Backend 补齐请求关联、允许公开的错误码和结构化诊断，避免任意内部错误直接外传；检查静默清理失败、非 root 容器、代理信任边界和并发改密/登录撤权。发布前验证部署实际值，而不只检查示例配置。

统一记录模型加载、路由、首输出、生成终态、取消、fallback、记忆检索与修订等事件。只保留必要的请求/模型/版本、耗时、结果与错误分类；账号标识和设备信息按最小化原则处理，明确本地保留、用户导出与清理规则。

默认不记录或上传完整 Prompt、Response、Authorization、原始记忆和模型回显的私人信息。真实聊天用于质量评测需要专门授权，开发用合成或明确许可的数据。

## 13. 首个 14 天的实际安排

以下以 Windows 环境、真机和固定模型包可用为前提；若验收失败，优先解决失败，不机械进入后续日期。

| 时间窗口 | 主线 | 配套工作 |
| --- | --- | --- |
| 第 1～3 天 | 确认完整版本、修复编译阻断、Windows/CI 基线 | 准备小型中文人格/记忆用例 |
| 第 4～8 天 | 模型生命周期/重试与账号/终止边界，两条线按风险取舍 | 持续交接并验证对应回归 |
| 第 9～14 天 | 固定设备完整模型/会话验收，建立最小真实性能记录 | 首次人格对照；门槛通过后才开始显式记忆 |

首个 14 天的目标交付物为：可信构建与问题状态、单设备端到端验收记录、小型人格评测基线。完成不了时缩小范围并保留未通过项，不用新功能替代验收。批式生成、磁盘缓存、GPU、自动 RAG 和完整社交网络不占用该轮主线。

## 14. 衡量与持续决策

| 维度 | 持续记录 | 决策用途 |
| --- | --- | --- |
| 用户流程 | 安装、首次聊天、创建/编辑、恢复成功与错误原因 | 确认用户能独立使用 |
| 稳定性 | 加载/生成失败、取消、崩溃、终态和数据丢失用例 | 决定是否允许扩功能 |
| 性能 | 首屏、Prefill、Decode、内存、取消和持续性能分布 | 选择有收益的 Runtime 实验 |
| 路由 | 可用路径、本地结果、fallback 原因、延迟与成本 | 调整规则，避免把执行成功等同质量合格 |
| 记忆 | 正确写入、证据召回、回答使用、冲突、过期、删除 | 判断是否需要摘要/向量/重排序 |
| 人格 | 一致性、语言/风格、重复、任务表现 | 防止升级破坏角色体验 |
| 隐私 | 边界回归、实际出站、跨账号和删除完整性 | 作为发布门槛 |
| 工程 | 可重复构建、测试结果、未验证项、回归与修复成本 | 控制迭代范围 |

隐私与数据完整性在既定回归集内要求无违规；这不等于宣称所有设备或输入绝对无风险。性能数值目标在第一轮基线后设定，附设备、样本和允许退化范围，避免使用没有依据的 Token/s 或毫秒承诺。

每个里程碑复盘：原问题是否解决、用户收益是否出现、哪些复杂度值得保留、下一项最大不确定性是什么。每次最多两条主线和一个受限实验；实验超过成本上限或未改善对照时停止。代码整理与文档跟随变更，不预设固定半年投入比例。
